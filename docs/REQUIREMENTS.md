# Requirements

Status: Draft v1 · Last updated 2026-06-21

This document captures the agreed scope. Each original requirement (R1–R10) is
restated, refined, and given acceptance criteria. New requirements discovered
during scoping are prefixed **N**. Non-functional requirements are **NFR**.

---

## Locked decisions (from scoping)

| Topic | Decision |
|-------|----------|
| LLM inference | **OpenRouter** (model-agnostic gateway). Use a vision-capable model for image queries. LLM access is abstracted behind one service so the model can be swapped. |
| Stack | **Python / FastAPI** full-stack. Server-rendered UI (Jinja2 + HTMX + Tailwind) for a mobile-first, low-JS experience. |
| Scope | **MVP — single lab, cloud-hosted** (managed PaaS). |
| QR | **Single global QR** for the lab. Machine is identified from the conversation and/or the uploaded image. |

## Functional requirements

### R1 — LLM answers from uploaded manuals
The system answers user questions about lab machines using an LLM.
- **AC1:** A user can send a text question and receive a relevant answer.
- **AC2:** Answers are generated by the LLM via the OpenRouter service layer.

### R2 — Strictly grounded RAG (no weights / no internet for answers)
Answers/solutions must come **exclusively** from retrieved document chunks.
- **AC1:** Every answer is produced from context retrieved from the vector store.
- **AC2:** System prompt forbids using outside/parametric knowledge; if retrieval
  returns nothing relevant, the assistant replies *"I couldn't find that in the
  available manuals"* (configurable) instead of guessing.
- **AC3:** No web/tool access is wired into the answer path.
- **⚠ Nuance (see Risks):** *Image interpretation* unavoidably uses model vision
  weights to "see" what's in a photo. The **instructions/solution** must still come
  from RAG. We treat vision as "convert image → text observations," then ground the
  answer in retrieved manual content.

### R3 — Image upload (incl. from phone)
Users can attach images (photo of a machine, an error screen, a part).
- **AC1:** Chat UI exposes a file/camera input that works on mobile browsers
  (`<input type="file" accept="image/*" capture="environment">`).
- **AC2:** Uploaded image is stored and passed to the vision model; extracted
  observations are used to retrieve relevant manual sections.
- **AC3:** Accepted formats (JPEG/PNG/HEIC→converted), max size enforced.

### R4 — Web app reachable via QR code
- **AC1:** App is a responsive website.
- **AC2:** A single QR code encodes the app URL (optionally with a lab token);
  scanning opens the login/chat page on a phone.
- **AC3:** A script regenerates the QR if the URL changes.

### R5 — Admin can see who accessed the tool
- **AC1:** Each session/login is recorded (user identifier, timestamp, IP, user-agent).
- **AC2:** Admin dashboard lists access events, filterable by date.
- *Note:* "users" are lightweight — see R10. Identity can be a self-entered
  name/email or an issued code; access log ties activity to that identity.

### R6 — Admin uploads/deletes documents
- **AC1:** Admin can upload a manual (PDF first; optionally DOCX/images).
- **AC2:** Upload triggers ingestion: parse → chunk → embed → index.
- **AC3:** Admin can delete a document; its chunks/embeddings are removed and it
  stops appearing in answers and citations.
- **AC4:** Admin sees ingestion status (queued/processing/ready/failed).

### R7 — Admin can see user chat history
- **AC1:** Admin can browse all chats, grouped by user/session.
- **AC2:** Each chat shows the full transcript, attached images, and which
  documents were cited.
- **AC3:** Searchable/filterable by date and user.

### R8 — Users can create new chats
- **AC1:** A user can start a new chat; prior chats remain accessible to them in
  their session.
- **AC2:** Each chat has its own message history passed as conversation context.

### R9 — Clickable document citations
LLM replies include clickable links to the source document(s).
- **AC1:** Each answer lists the source document(s) used.
- **AC2:** Clicking a citation opens/downloads the original document.
- **AC3:** Where possible, the link deep-links to the page/section (e.g. `#page=12`).

### R10 — Security: user temp password + separate admin password, both changeable
- **AC1:** Users authenticate with a shared **temporary lab access password**
  (rotatable by admin).
- **AC2:** Admin authenticates with a **separate** password.
- **AC3:** Admin can change **both** the user password and the admin password.
- **AC4:** Passwords are stored hashed (never plaintext); sessions use signed
  tokens/cookies.

## Accepted requirements (decisions recorded)

All of the below are **in scope** for the MVP.

- **N1 — Citation integrity (accepted):** answers may only cite documents actually
  retrieved for that turn (prevents fabricated links).
- **N2 — Rate limiting / abuse protection (accepted — layered):** **edge/platform**
  (Cloudflare/WAF) for blunt abuse + DDoS, **and** **app-level** (`slowapi`) for
  precise per-endpoint throttling on login and chat. The shared user password is a
  weak secret (see Risks), so login throttling is mandatory.
- **N3 — Image retention (accepted — keep until admin deletes):** user-uploaded
  photos are retained **indefinitely**; there is **no automatic expiry**. Deletion is
  a deliberate admin action (single image, a chat's images, or bulk). Admin UI must
  expose a delete control. *Note:* document this clearly to users — photos may show
  people/screens and are kept until removed.
- **N4 — Ingestion (accepted — synchronous):** parsing/chunking/embedding runs
  **inside the upload request**; the admin sees the final `ready`/`failed` result on
  completion. Per-document status + ingestion logs still recorded so a garbled manual
  is visible. *Trade-off accepted:* very large PDFs may be slow/time out — revisit a
  background task if that becomes a problem (enforce a sane max file size meanwhile).
- **N5 — "No answer" telemetry (accepted):** log when the bot returns *not found* so
  the admin knows which manuals to add (supports the "review effectiveness" goal).
- **N6 — Feedback control (accepted):** 👍/👎 per answer to measure effectiveness.
- **N7 — Per-user chat isolation (accepted):** a user cannot see another user's
  chats; only admin sees all.

## Non-functional requirements

- **NFR1 — Mobile-first:** primary device is a phone in a lab; UI must be usable
  one-handed, large tap targets, works on iOS Safari + Android Chrome.
- **NFR2 — Latency:** first token / answer within a few seconds for typical queries.
- **NFR3 — Cost control:** track token usage per request; cap context size.
- **NFR4 — Portability:** LLM and embedding providers behind interfaces; vector
  store swappable (start with pgvector).
- **NFR5 — Security baseline:** HTTPS only, secrets in env vars, hashed passwords,
  signed sessions, input size limits, file-type validation.
- **NFR6 — Auditability:** access log + chat log retained for admin review.
- **NFR7 — Data residency:** document the fact that OpenRouter routes prompts +
  images to third-party model providers (relevant if manuals are confidential).

## Risks & open questions

- **Shared user password is a weak control.** Anyone with the QR + password is "a
  user," and access logs only mean anything if users self-identify honestly.
  *Alternatives:* per-visit issued codes, magic-link via email, or SSO if the lab
  has it. Decide before R5/R10 are considered "done."
- **Single global QR + machine disambiguation.** With one QR, the system must infer
  the machine. Mitigations: ask the user to name/select the machine, use the photo,
  or tag manuals by machine and add a lightweight machine picker. Per-machine Q
  remains a strong later upgrade.
- **"No internet/weights" vs. vision.** Confirm stakeholders accept that image
  *interpretation* uses model weights while *answers* stay RAG-grounded.
- **OpenRouter & confidentiality.** Confirm manuals/photos may leave the network. If
  not, this pushes toward a self-hosted model + on-prem deploy (out of MVP scope).
- **Embeddings provider.** Local sentence-transformers (free, private) vs. hosted.
  MVP default: local model to avoid extra API and keep document text in-house.
- **HEIC images** from iPhones need server-side conversion.
